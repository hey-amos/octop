# 发布生命周期

仅在准备发布、发布修复或回流时读取。本技能规定分支生命周期；发布包、镜像、桌面包和部署目标要依据本次实际要求落实，不凭上游配置推断目标。

## 创建和冻结

1. 读取最新 `develop`、相关检查和本次发布范围。需要同步上游时，先完成 develop rebase 和验证，再切发布分支。
2. 从准确的 `develop` SHA 创建 `release/<本次版本标识>`。记录分支名、切出 SHA、对应上游基线、发布范围和状态；与 rebase 记录一样保存到 Git common-dir 的 `develop-fork/` 中，交付给用户可核对的记录位置。
3. 从此暂停 `develop` 对 `main` 的 rebase，直到所有活动发布完成回流；`main` 可继续同步，`develop` 可集成下一轮功能。
4. 只在 release 中做发布修复、版本和 fork 发布说明、必要的打包调整，不 rebase 到 develop，不夹带之后合入 develop 的新功能。fork 发布说明维护在 `docs/fork/` 的对应记录中，不追加到上游根 `CHANGELOG.md`。

若用户要求引入冻结后新增的上游改动，先明确这是调整发布基线；不能悄悄继续原冻结流程。保留原快照，按明确的新范围重新准备和验证。

## 发布前确认实际目标

- `v*` 只属于上游。本项目尚未约定定制标签命名：沿用用户提供的独立命名空间；没有时先完成可独立进行的准备，再确认标签名和发布目标。`fork/...` 只是可选示例，不是自动批准的规范。Git 标签名、Python 包版本和镜像标签是不同约束，不能直接互相套用。
- 检查冻结提交的版本信息与制品元数据。说明所基于的上游版本及 SHA，避免把开发中的上游 main 冒充某个正式上游 tag。
- 检查相关 `.github/workflows/` 和远端实际启用状态。现有 `release.yml` 会发布包并级联 `sync-main-to-develop.yml`，后者采用 merge/重建而非本方案的 rebase；`auto-tag-on-release.yml` 面向 release 合入 main。不得借这些上游流程发布定制版，也不能因自定义标签不匹配 `v*` 就声称它会自动发布。
- 发布触发器、仓库、包名、镜像地址、制品位置及副作用应与授权一致；工作流修改、启停、发布凭据和分支保护不自动配置。缺少目标信息时只暂停实际发布，保留准备成果。
- 按项目要求验证冻结提交。实际推送或发布前核对分支 tip 未变化；测试后又改内容必须重新进行相关验证。

已获发布授权且命名、目标、工作流都明确时，从已验证的 release SHA 创建定制标签并执行指定发布。标签对象固定；后续 develop rebase 不移动它。失败时先查远端和制品状态，不能重复创建或覆盖既有版本。

## 发布后回流

确认发布成功后，将 release 中新增的修复和发布准备改动合回 `develop`。不合入 `main`，不 rebase 已发布的 release，也不把标签挪到合回后的提交。

1. 保存发布 tip 和标签对象 ID，检查创建时的切出 SHA 仍是当前 `develop` 与 release 的祖先；否则说明冻结期间发生了历史变化，暂停普通合回，按记录核对待回流提交。
2. 若 release tip 已是 `develop` 的祖先，无需重复合入；若 develop 是 release tip 的祖先，优先 `git merge --ff-only`。
3. 若 develop 已接收下一轮功能而与 release 分叉，默认在 develop 用 `git merge --squash` 合入冻结 release tip，然后创建回流提交，保持 develop 线性。检查冲突与版本元数据，保留 develop 的新功能，不能用 release 整棵文件树覆盖 develop。用户指定其他合入方式时，说明其对后续 rebase 的影响再执行。
4. 验证回流结果，记录 release tip 与回流提交的对应关系。squash 后 release tip 不必是 develop 的祖先，不能仅凭祖先检查声称“未回流”；以差异、回流记录和验证结果判断，避免重复 squash。
5. 确认发布引用固定、全部改动已回流且没有未保存工作后，按任务授权清理 release 分支。squash 后 `git branch -d` 可能拒绝，不能盲目改用 `-D`；先提供上述保留证据再做精确删除。远端删除需在授权范围内，并核对远端 tip 未被更新。
6. 将发布记录标记完成，并在 `docs/fork/` 的对应记录中补充实际标签、上游基线、制品和验证结果。其他活动发布都结束后，恢复 develop 对 main 的 rebase，再按授权更新其他 feature 分支。此时即使 develop 的提交 SHA 改变，已发布标签和制品仍对应原冻结快照。

发布失败、回流未完成、远端状态未核实或仅创建本地标签，都不能报告“发布流程完成”。
